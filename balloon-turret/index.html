Balloon-Tracking Laser Turret

A webcam finds a balloon, a laptop predicts where it's going, and an Arduino swings a pan/tilt turret to follow it. A pointer-grade laser may only switch on when the turret holds a steady lock and every safety check passes.

Software complete and tested in simulation · hardware build in progress at the SCU Maker Lab

What's simulated: the webcam and detector (the balloon's true position plus a little noise, 30 frames per second, an occasional missed frame) and the servos (400°/s, after the delay you set). Everything between them is ported from the Python tracker, so the scores here are close to, but not the same as, the project's own test results, which run the real code on rendered video. The fast toss is there on purpose: a 30 fps camera and hobby servos can't catch it, which is one of the project's known limits. Webcam mode swaps the simulated balloon for your camera and a JavaScript port of the project's color detector (same color presets and click-to-pick). The turret itself stays simulated, like the project's --dry-run mode.

How it works

Webcam30 fps; a background thread keeps only the newest frame
frames
Laptop · Python + OpenCVdetect → predict → aim → lock → decide whether the laser may fire
USB serial
Arduino Unopan/tilt servos, laser, LOCKED LED, fire button, 500 ms watchdog

  1. Detect

    A YOLOv8 model or HSV color thresholds find the balloon. Color detection handles red's hue wrap-around, loosens a little for motion blur, and ignores tiny bright laser dots and look-alikes far from where the balloon should be.

  2. Predict

    Two Kalman filters run side by side, one for steady motion and one for accelerating motion (falling, bouncing). Whichever predicted better gets more weight each frame (an IMM filter), so a falling balloon is followed by the acceleration model automatically.

  3. Aim

    Each frame the turret moves at the balloon's own speed (feedforward) plus a correction for the leftover error. It aims ahead by the measured latency plus the servo delay. The correction strength rises with tracking confidence and is capped below the point where the delay would make it oscillate.

  4. Lock

    The real detection (never just the prediction) has to stay inside a lock zone for 5 frames in a row. The zone scales with how big the balloon looks, and leaving it takes a bigger circle so one noisy frame doesn't drop the lock.

  5. Decide

    One function, laser_should_fire(), is the only place in the code that can turn the laser on.

The auto-tuner runs the real tracker headless against simulated falls, bounces, throws and drifts at 30 and 60 fps, and searches 150 parameter sets for the best mix of accuracy, time locked and stability.

Safety

The laser is pointer-grade (under 5 mW) and the turret only runs with nobody in its field of view. In code, the laser fires only if every one of these is true on that frame:

  • real detection, not a prediction
  • locked for 5 frames
  • no vision fault
  • watchdog OK
  • window focused
  • balloon not too far
  • not calibrating
  • not a first run
  • Arduino connected
  • fire button held (Manual mode)
  • Off by default. LASER_ENABLED = False in both the Python code and the Arduino sketch. Nothing can fire until both are changed on purpose.
  • Two watchdogs. If the Python loop stalls for 200 ms, a separate thread sends laser-off. If the Arduino hears nothing for 500 ms, it turns the laser off itself.
  • Kill key. Q turns the laser off first, then the LED, then glides the turret home. Closing the window or any error does the same.
  • Tested. Each rule has a test that proves it. To check the tests themselves, I broke the safety code five different ways and confirmed the suite caught every one.

What I learned

The turret "lagged", and it turned out to be four different problems that looked like one:

The picture froze while a key was held

OpenCV reads one key per frame, so held-key repeats piled up in Windows' message queue and the window stopped repainting. Reading every waiting key each frame fixed it.

Old frames

Webcam drivers queue frames, so a slow loop works on pictures that are already old. A thread that keeps only the newest frame cut frame age from 72 ms to 9 ms.

The AI is the slowest part

About 14 fps against a 30 fps camera. Running it every third frame, with a fast color tracker in between, keeps up.

Proportional control always trails

Raising the gain just causes overshoot. Matching the balloon's speed (feedforward) plus a small lead for the delay fixed it.

The lesson: measure before fixing. The built-in timing report exists because guessing kept pointing at the wrong problem.
